# Betweenly 项目说明书

版本：v0.1（迁移基线）  
日期：2026-10-24  
中文名：之间  
原暂用名：直男聊天 Agent

## 1. 项目概述

本项目面向在接触喜欢的人时，不知道如何开场、自然交流或进一步发展关系的用户，提供结合具体背景的社交建议。

产品从聊天辅助切入，逐步覆盖认识、相互了解、邀请见面、线下相处、表达好感和互动回顾。

系统使用大语言模型，结合预设规则、双方偏好与边界、结构化 JSON 输出和程序校验，为用户提供：

- 当前可以采取的行动；
- 符合用户本人语气的表达；
- 支持建议的具体依据；
- 信息不足之处和后续选择。

核心目标是帮助用户自然表达、了解彼此，并选择合适的下一步。

## 2. 核心场景

### 2.1 刚认识，不知道如何开始

双方以前不认识或交流很少，刚加好友，用户不知道从哪里聊起，也担心主动联系显得唐突。

系统需要了解：

- 通过什么渠道认识；
- 加好友前有过哪些交流；
- 是否有真实的共同经历或兴趣；
- 用户此次联系的目的。

系统提供开场、接话和结束交流的建议，帮助双方建立联系。

### 2.2 已经认识，希望进一步发展

双方持续交流，用户希望更熟悉、单独见面或表达好感，但不知道何时、如何行动。

系统需要了解：

- 用户所说的“推进”具体指什么；
- 双方是否都会主动联系；
- 是否单独见过面；
- 是否邀请或表达过，对方如何回应；
- 对方是否表达过明确边界。

根据背景，建议继续了解、提出邀请、表达意愿、放缓节奏或补充信息。

这两类是核心场景；同一用户可在不同阶段使用不同功能，也可以只描述一次线下事件，无须上传聊天记录。

## 3. 产品范围

| 环节 | 典型需求 | 产品帮助 |
|---|---|---|
| 建立联系 | 刚认识，不知道如何开口 | 寻找真实切入点，准备开场 |
| 相互了解 | 话题单一，交流像问答 | 帮助分享经历、延伸话题 |
| 提出邀请 | 不知道怎么约、约什么 | 设计具体且方便回应的邀请 |
| 见面准备 | 紧张、担心冷场 | 整理活动安排和交流思路 |
| 线下相处 | 不会倾听或表达自己 | 提供情境练习和事后反馈 |
| 表达好感 | 不知道怎样说明意愿 | 帮助清楚、自然地表达 |
| 互动回顾 | 不知道接下来怎么做 | 根据真实结果调整建议 |
| 分歧与拒绝 | 不会解释、道歉或收尾 | 帮助承担责任、尊重边界 |

## 4. 核心功能

### 4.1 背景整理与目标确认

用户输入聊天、线下经历或当前困惑，系统整理已有信息，只补问会影响建议的关键问题。不强制用户先填写完整问卷，也不凭少量消息确定关系阶段。

### 4.2 下一步行动建议

系统优先回答“现在可以做什么”。建议可以是开启或延续交流、分享真实经历、提出具体邀请、表达感受与意愿、澄清误会、放缓节奏、接受拒绝，或先补充背景。

每次优先给出一个主建议和必要的备选，并说明适用条件。

### 4.3 自然表达辅助

有用户草稿时优先轻微修改；没有草稿时提供少量有明显区别的候选。支持“太人机”“太油”“不像我”“太长”“理解错背景”等反馈，并在用户确认后调整表达偏好。

### 4.4 邀请与见面准备

结合双方已知兴趣、熟悉程度、时间和预算，帮助准备邀请与简单安排。第一版优先整理用户已经选择的活动；场所搜索、营业时间、路线和订位后续再接实时数据源。

### 4.5 互动回顾

用户自愿记录发生了什么和自己的感受。系统必须区分事实与推测，例如：

- 事实：对方接受了周六喝咖啡的邀请。
- 推测：对方有恋爱意愿。

系统根据事实更新建议，避免反复推荐已被拒绝的行动，同时关注用户是否也喜欢这段相处、是否感到被尊重。

## 5. 双方偏好与边界

系统逐步了解双方，但不能用固定人格标签代替具体信息。

| 维度 | 记录内容 |
|---|---|
| 兴趣偏好 | 明确表达过的兴趣、活动和饮食偏好 |
| 表达习惯 | 直接或含蓄、句子长短、表情使用习惯 |
| 玩笑偏好 | 哪些玩笑曾被接受，哪些明确不喜欢 |
| 明确边界 | 不喜欢的称呼、话题或互动方式 |
| 情境限制 | 忙碌状态、情绪、公开或私下场合 |
| 用户自身 | 用户的意愿、舒适程度和表达风格 |

每条记录包含来源、时间和适用情境，并区分：

1. 对方明确表达；
2. 用户自述或转述；
3. 观察到的行为；
4. 待确认的推测。

模型推测不能自动写成已确认事实。档案允许查看、修改、删除；存在冲突时保留差异并补问。

玩笑与边界规则：

- 明确表示不喜欢的内容，优先遵守。
- 一次“哈哈”、笑脸或没有反对，不能证明接受。
- 曾经接受，不代表所有时间和场合都接受。
- 信息不足时，不主动推荐针对个人敏感点的调侃。
- 不能通过逐步冒犯来测试底线。

## 6. 自然表达标准

判断建议是否合理与说话是否自然，需要分别检查。生成表达应当：

- 接住对方说过的具体内容；
- 符合双方熟悉程度；
- 保留用户自己的语气；
- 不编造经历或无依据地安慰；
- 不连续盘问；
- 不机械添加“哈哈”“啊”和表情；
- 将解释与准备发送的文案分开展示。

这些是情境规则，不是统一模板。重要解释和道歉需要足够内容，不能一律追求短句。

## 7. 建议必须有依据

每条建议应包含：

| 内容 | 作用 |
|---|---|
| 建议行动或表达 | 告诉用户可以怎样做 |
| 简短理由 | 解释为什么适合当前背景 |
| 信息来源 | 指向具体聊天、事件或用户说明 |
| 不确定性 | 说明哪些事情尚不知道 |
| 后续选择 | 根据对方回应调整行动 |

理由必须能被用户检查和纠正，避免“某类人都喜欢这样”的泛化解释。不输出缺乏可靠依据的“喜欢概率”“脱单成功率”等数字。

## 8. 技术方案

### 8.1 总体流程

`用户输入 → 整理相关背景 → 调用 LLM → 校验 JSON → 展示建议 → 用户编辑与反馈`

| 部分 | 职责 |
|---|---|
| 大语言模型 | 理解语境、提出建议、生成表达 |
| 预设规则 | 规定分析维度、行为要求和边界 |
| 后端程序 | 校验结构、引用、访问权限及异常 |
| 前端界面 | 收集背景，展示建议与依据，接收反馈 |

第一版不训练或微调模型。模型供应商、版本与技术栈待原型评测后确定。建议先用一次调用完成分析和生成；是否增加独立审核调用，由实际失败模式决定。

### 8.2 输入结构

主要字段包括：

- `scenario`：刚认识、进一步发展或具体困难；
- `user_goal`：用户具体目标；
- `background`：关系背景；
- `messages`：带角色和 ID 的聊天；
- `events`：线下事件；
- `preferences`：偏好与边界；
- `user_style`：用户表达习惯。

未知信息保留未知，不猜测补全。

### 8.3 输出结构

核心字段包括：

- `status`：`ok`、`needs_context` 或 `error`；
- `observations`：带证据引用的观察；
- `uncertainties`：当前未知；
- `recommendation`：主行动、理由、证据和后续分支；
- `reply_options`：少量表达候选；
- `clarifying_questions`：会改变建议的关键追问。

信息不足时返回 `needs_context`，允许没有回复候选。线下行动建议也不必强行附带聊天文案。正式草案见 `schemas/`。

### 8.4 校验与异常处理

程序检查 JSON、字段类型、枚举、长度、数量、引用是否存在、字段一致性，以及空响应、截断、超时和调用失败。失败时有限重试；持续失败则提示重新分析并保留用户输入。

结构正确不等于内容正确。引用是否支持结论、表达是否自然，需要额外评测。聊天记录属于分析材料，不能作为系统指令执行。密钥保存在后端且不得提交到仓库。

## 9. 数据与隐私

第一阶段数据主要用于示例、规则改进和评测。优先采用人工虚构案例、人工角色扮演、人工审核后的合成案例，以及获得相应用途授权的真实案例。

“本次分析”“长期记忆”“训练或公开贡献”必须分别授权，不能默认互通。原始聊天默认不长期保存；长期档案由用户选择，并支持查看、修改和删除。外部模型调用需要说明发送哪些内容并减少无关信息。

GitHub 演示仅使用虚构或明确获准公开的案例。

## 10. 第一版验收

用相同场景比较基础提示词方案和完整方案，匿名评价：

| 维度 | 检查重点 |
|---|---|
| 事实准确性 | 是否编造、混淆角色和时间 |
| 建议适切性 | 是否符合背景，是否应先补问 |
| 证据有效性 | 来源是否真正支持结论 |
| 自然程度 | 是否像日常表达、像用户本人 |
| 边界尊重 | 是否违背明确偏好或拒绝 |
| 工程可靠性 | 协议、异常、延迟和成本 |

重点覆盖信息不足、明确拒绝、玩笑边界未知、偏好冲突、线下事件和指令注入。开发案例与独立评测案例分开，同一聊天及其改写不能跨组。回复率、赴约率和恋爱结果不能单独证明产品效果。
