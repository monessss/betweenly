# Betweenly（之间）

一个面向真实社交情境的行动与表达助手。它帮助用户整理背景、判断当前更合适的下一步，并生成符合本人语气、尊重双方边界的表达建议。

> 当前状态：产品与协议基线。尚未接入模型、前端、数据库或部署环境。
> 

## 为什么我们要做 Betweenly？

**每一段关系，都始于一次对话。但有时候，最难的恰恰是开口。**

Betweenly 的诞生，源于一个很个人、也很真实的经历。

我曾经是一个不太会和女生聊天的男生。

遇到一个想要认识的人，却不知道该如何开口；好不容易开始了一段对话，却不知道怎样才能让话题继续下去；明明想更进一步地了解对方，想让她开心，想让两个人的关系慢慢变得亲近，却总是担心自己说错话，担心自己太无聊，也担心表现得过于刻意。

有时候，为了一条消息，我可以反复斟酌很久；有时候，一段对话结束后，我会忍不住回想自己是不是说错了什么；有时候，看着别人轻松自然地和喜欢的人聊天，我也会想，为什么一件在别人看来再普通不过的事情，到了自己这里，却变得这么困难？

后来我渐渐意识到，很多时候，我们并不是没有真心，也不是没有想表达的东西。

**我们只是还没有学会，如何把心里的话，用恰当的方式说出来。**

我们想靠近一个人，却不知道怎样迈出第一步；我们想了解一个人，却不知道如何让对话不止于表面；我们想表达关心，却担心自己的话显得生硬；我们想让对方感受到自己的真诚，却常常因为不知所措而错失机会。

也正是因为这些真实的困惑，我们开始构思 Betweenly。

我们希望打造一个真正理解聊天场景的 AI Agent，帮助那些不擅长沟通、容易过度思考、却依然真诚地期待建立一段关系的人。

无论你是刚认识一个女生，不知道如何破冰；还是已经聊了一段时间，却不知道如何让关系更进一步；又或者面对对方的一句话，想了很久依然不知道怎样回复，Betweenly 都希望能陪你一起分析当下的情境，理解对方可能的想法，找到更自然、更合适的表达方式。

但我们不想做一个只会生成聊天话术的工具。

我们不认为一段关系应该被简化成套路、技巧，或者一套让对方喜欢上你的公式。我们也不希望用户只是机械地复制 AI 给出的答案，依赖它完成每一次对话。

比起告诉你下一句话应该怎么说，我们更希望帮助你理解：**为什么可以这样说，对方可能会有什么感受，以及在什么情况下，你应该换一种方式表达。**

我们希望 Betweenly 能帮助你逐渐了解一个人的性格与沟通习惯，理解对方的情绪和边界，在适当的时候表达关心、分享幽默，也在不合适的时候学会尊重与退让。

因为真正的亲近，从来不是靠几句精心设计的话术换来的，而是在一次次真诚的交流中，慢慢建立起来的。

我们知道，AI 无法替代真实的感情，也无法保证一个人一定会喜欢你。每个人都有自己的想法、偏好与选择，而这些都应该被尊重。

Betweenly 不能替你建立一段关系，但它可以帮助你迈出第一步；不能替你表达真心，但它可以帮助你找到表达真心的方式；不能保证每一次聊天都有完美的结果，但它可以让你在面对不确定时，多一点理解，少一点不知所措。

**我们想为那个有很多话想说，却不知道如何开口的男生，做一点真正有用的事情。**

为那个因为一条消息反复思考的男生，为那个面对沉默不知道如何继续的男生，也为那个明明很真诚，却总是无法让别人理解自己的人。

我们希望有一天，你不再需要为了每一条消息绞尽脑汁，不再因为不擅长聊天而否定自己，也不再觉得建立一段关系是一件遥不可及的事情。

你可以慢慢学会理解别人，也慢慢学会表达自己。

你不需要变成另一个人，才值得被别人了解。你需要的，或许只是一些帮助，让你能够更自然地展现真实的自己。

这就是我们做 Betweenly 的初衷。

**Betweenly —— 少一点纠结，多一点理解，让每一次靠近都更加真诚。**

## 核心原则

- 先解决“现在可以做什么”，再给可直接使用的表达。
- 建议必须引用具体消息、事件或用户说明作为依据。
- 明确区分事实、用户转述、观察和待确认的推测。
- 信息不足时承认未知并只追问会改变建议的关键问题。
- 尊重拒绝、边界和双方自主选择，不提供操控、纠缠或试探底线的策略。
- 优先轻改用户草稿，不把所有人改成同一种“标准话术”。

## 第一版范围

三个主要入口：

1. 我想认识她/他
2. 我想进一步了解她/他
3. 我遇到了具体困难

第一版计划包含背景输入、偏好与边界档案、下一步行动建议、表达辅助、证据说明、编辑反馈和互动回顾。

暂不包含自动发送、后台监听、成功率预测、自动订位，以及未经授权的真实聊天训练。

## 推荐开发顺序

1. 用虚构案例补齐两类核心场景，以及邀请、见面准备、拒绝和回顾场景。
2. 根据案例迭代输入/输出 Schema，并实现跨字段与证据引用校验。
3. 做一个最小后端：接收结构化输入、调用模型、校验输出、有限重试。
4. 做一个最小界面：输入背景、展示建议与依据、允许修改和反馈。
5. 用独立测试集对照基础提示词，记录失败案例后再决定技术栈与模型。
